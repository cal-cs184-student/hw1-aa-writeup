Task 1: Drawing Single-Color Triangles

How I rasterize triangles

By the time a triangle reaches rasterize_triangle, its three vertices \(P_0, P_1, P_2\) are already in screen space (pixel units, floating point). My rasterizer turns that continuous triangle into a set of covered pixels in three steps.

  1. Bounding box. I take the minimum and maximum of the vertices' \(x\) and \(y\) coordinates, round them outward to whole pixels, and clamp the result to the framebuffer. Only pixels inside this box can possibly be covered, so they are the only ones visited; parts of a triangle that fall off screen cost nothing.
  2. One sample per pixel, at the pixel center. For pixel \((x, y)\) the sample point is \((x + 0.5, y + 0.5)\), not the pixel's corner.
  3. Three line tests. For the edge from \(P_i\) to \(P_j\), with \(\Delta x_{ij} = x_j - x_i\) and \(\Delta y_{ij} = y_j - y_i\), the line equation \[ L_{ij}(x, y) = (y - y_i)\,\Delta x_{ij} - (x - x_i)\,\Delta y_{ij} \] is the 2D cross product of the edge vector with the vector from \(P_i\) to the sample. It is zero on the line through the edge and has opposite signs on its two sides. A sample is inside the triangle exactly when it lies on the same side of all three edges.

Which sign counts as "inside" depends on the winding order: counter-clockwise and clockwise triangles give opposite signs. Instead of reordering vertices, I accept a sample when all three values are \(\ge 0\) or all three are \(\le 0\), so both windings render correctly (svg/basic/test6.svg checks this). Because the comparisons include equality, a sample lying exactly on an edge counts as inside, so no edge is left un-rasterized and two triangles that share an edge never leave a crack between them. Every covered pixel is written with fill_pixel, and resolve_to_framebuffer later converts the stored colors to 8-bit RGB for display.

Why this is no worse than checking every sample in the bounding box

My basic implementation is the bounding-box algorithm: it visits every pixel inside the triangle's bounding box exactly once and does a constant amount of work per pixel (three line equations and a sign check). Its cost is therefore proportional to the area of the bounding box, and it never scans the whole framebuffer. The bounding box is also clamped to the screen, so it can only shrink.

The optimized version described in the extra credit below goes further: on each row it tests only a sub-range of the bounding box's pixels, and the extra bookkeeping is a constant amount of work per row. Since it tests a subset of the same samples with the same test, it never does more per-sample work than the bounding-box algorithm.

Result: basic/test4.svg

The magenta triangle is one continuous shape, but near its top vertex it is narrower than a pixel. With only one sample per pixel, a pixel is filled only if its exact center falls inside the triangle, and most centers there miss it. In the inspector, the triangle shows up as a short isolated run of pixels, then a gap, then the rest of the triangle; the right tip of the thin red triangle breaks into scattered pixels for the same reason. This is aliasing: a single point sample cannot represent geometry smaller than a pixel. Supersampling in Task 2 addresses it.

Extra credit: a faster triangle rasterizer

The reference images are compared byte-for-byte, so I set one hard constraint: the optimized rasterizer must produce exactly the same pixels as the basic one. That ruled out the classic incremental trick of adding a constant to each edge value per pixel, because accumulated floating-point error flips samples that lie right on an edge. Within that constraint I made four changes.

  1. Per-row spans instead of the full bounding box. On a fixed row \(y_s\), the term \(r_k = (y_s - y_k)\,\Delta x_k\) of edge \(k\)'s line equation is a constant, so the equation is a linear function of the sample's \(x_s\): \[ L_k(x_s) = r_k - (x_s - x_k)\,\Delta y_k. \] The sign of the triangle's signed area tells me which sign means "inside", so each edge's inside condition becomes a half-line, \(x_s \le x_k + r_k / \Delta y_k\) or \(x_s \ge x_k + r_k / \Delta y_k\) depending on the sign of \(\Delta y_k\). Intersecting the three half-lines gives the interval \([lo, hi]\) that the triangle covers on that row, and I only test pixels in that interval. A horizontal edge (\(\Delta y_k = 0\)) either accepts or rejects the entire row, so rejected rows are skipped without testing any pixel.
  2. Exact results despite rounding. The span only decides which pixels to test. I pad it by one pixel on each side, and every pixel in it still goes through the original three line tests, so rounding error in \(lo\) or \(hi\) can never add or drop a sample. Degenerate triangles (zero area) have no meaningful inside sign, so they fall back to the plain bounding-box scan and behave exactly as before.
  3. Hoisting loop-invariant work. The edge vectors \(\Delta x_k, \Delta y_k\) are computed once per triangle, and the \(y\)-only term \(r_k\) once per row, leaving one subtraction, one multiplication and one more subtraction per edge in the inner loop. Writing \(-ab + r\) as \(r - ab\) is bit-for-bit identical in IEEE floating point, so this does not change the output either.
  4. Cheaper setup. The bounding box is clamped in floating point before converting to integers, so vertices far off screen cannot overflow an int, and triangles that are entirely off screen return immediately.

To check correctness, I rendered all 32 provided SVGs plus 8 randomly generated stress scenes with both versions and compared the PNG files byte-for-byte: all 40 were identical. The stress scenes target the risky cases: 3000 random triangles of both windings, 3000 long slivers, 3000 degenerate triangles (collinear or repeated vertices), vertices on integer and half-integer coordinates (so edges pass exactly through sample points), sub-pixel triangles, and huge triangles reaching \(\pm 10^6\) pixels. The provided reference tests that passed before still pass.

Timings are the average of 20 consecutive svg.draw() calls in DrawRend::redraw() (measured with std::chrono::high_resolution_clock), median of 3 runs; Release build (MSVC /O2) on an Intel Core i9-12900H, 1024 × 1024 framebuffer, 1 sample per pixel.

The speedup tracks how much of a triangle's bounding box is empty. A typical large triangle covers roughly half of its box, so skipping the empty half (together with the hoisting) gives about 2–3x on the provided illustrations and on random large triangles. Long thin triangles are the extreme case: 02_degenerate_square2.svg is a fan of 1000 slivers from one corner of the canvas, each only one SVG unit wide at its far end but with a bounding box that can cover most of the canvas, so almost every sample in those boxes is wasted by the basic version; the span version is 36x faster, and thin diagonal triangles reach almost 50x. The one case with no gain is sub-pixel triangles: their bounding box is only one or two pixels, there is nothing to skip, and the per-row span setup costs slightly more than it saves.
